## 1. Was sich gegenüber Spec G ändert

| Spec G | G2 |
|---|---|
| §6.3: Auswertung am Desktop nach jedem Preisschreiber **und** in der Cloud nach der Tagesaktualisierung, Dedup über beide | **Ein** Auswerter nur in der Cloud: Edge Function `evaluate-price-alerts`, stündlich per `pg_cron`. Desktop und Handy lesen nur. |
| §5.4: `global_move` + `above`/`below`, Unique über `found_at` | `kind` ∈ `move`/`above`/`below`; Dedup über `day`; Zielpreise mit `armed` (einmal pro Überschreiten); Bewegungsalarm einmal pro Fenster. |
| §6.3: Electron-`Notification` pro Preisschreiber | Benachrichtigung aus dem Sync-Zyklus für neue Treffer, lokale Marke `price_alerts_notified_until`. |
| §7.1/§7.2: Liste „Tipp → Liste" ohne Ort | Alarmliste als eigener Reiter „Alarme" in Insights (Desktop und Handy). |
| Begriff „Preis-Alerts" | „Preis-Alarm"; die Desktop-Seite „Deals & Preis-Alerts" heißt „Deals". |

**Befunde des Code-Abgleichs (2026-09-14):** `apply_cardmarket_prices` gibt nur eine Anzahl zurück; die Desktop-Preisschreiber liefern keine geänderten Printings; `Notification` ist in `main.cjs` importiert, aber ungenutzt; am Handy gibt es keine Benachrichtigungs-Infrastruktur (kein FCM, kein WorkManager); `cards`/`card_copies`/`price_history` haben kein `user_id` (Einzelnutzer-Modell), Deals-Tabellen schon.

## 2. Umfang

**Drin:**
- Bewegungsalarm (eine Regel pro Nutzer: ab `pct` % und ab `min_eur` € in `days` = 7 oder 30 Tagen) und Zielpreise pro Printing (≥ / ≤).
- Treffer-Liste auf beiden Geräten, „Erledigt" pro Treffer und „Alle erledigt".
- Start-Karte „Preis-Alarme (N)" (nur bei offenen Treffern), Insights-Reiter „Alarme", Alarm-Zeile im Kartendetail, Einstellungen › Preise › Preis-Alarme.
- Windows-Benachrichtigung am Desktop für neue Treffer.
- Umbenennung der Desktop-Seite „Deals & Preis-Alerts" → „Deals".

**Nicht drin:** Push aufs Handy (kein FCM; Treffer erscheinen beim Öffnen), Alarme auf Sealed (G3) und 1st-Edition-Preise (G4), Alarme auf nicht besessene Karten (Wunschliste bleibt Deals).

**Erfolgskriterium:** Ein Zielpreis wird überschritten, ohne dass der Desktop läuft; spätestens nach dem nächsten stündlichen Lauf steht der Treffer am Handy; der Desktop zeigt ihn beim nächsten Start und meldet ihn höchstens einmal.

## 3. Architektur

- **Auswerter:** Edge Function `supabase/functions/evaluate-price-alerts/` (`index.ts` lädt und schreibt, `alerts.ts` reine Regel, `families.ts` Familienzuordnung), Service-Role wie `scrape-deals`, optionales Geheimnis `ALERTS_TRIGGER_SECRET` im Header `x-alerts-secret`, `pg_cron` stündlich um :15 (im Muster des Jobs `refresh-cardmarket-prices`).
- **Leser:** Desktop über den bestehenden Cloud-Client (`dealsClient()`/`sync.ensureClient()`), Handy per REST (`cloud/PriceAlertsRepository.kt`).
- **Folge:** Ohne Cloud-Sync keine Alarme (wie Deals). Desktop-seitige Preisänderungen lösen frühestens beim nächsten Lauf nach dem Hochschieben aus.

## 4. Datenmodell (nur Supabase)

### 4.1 `public.price_alert_rules`
| Spalte | Typ / Regel |
|---|---|
| `id` | `bigint generated by default as identity primary key` |
| `user_id` | `uuid not null default auth.uid()` |
| `kind` | `text not null check (kind in ('move','above','below'))` |
| `card_id, set_code, language, rarity` | `text`; bei `move` null, bei `above`/`below` pflicht (`check`) |
| `pct` | `numeric`, bei `move` pflicht, `check (pct between 1 and 500)` |
| `min_eur` | `numeric`, bei `move` pflicht, `check (min_eur >= 0)` |
| `days` | `integer`, bei `move` pflicht, `check (days in (7, 30))` |
| `threshold` | `numeric`, bei `above`/`below` pflicht, `check (threshold > 0)` |
| `armed` | `boolean not null default true` |
| `active` | `boolean not null default true` |
| `created_at`, `updated_at` | `timestamptz not null default now()`; `updated_at` per Trigger `set_updated_at` |

- Höchstens eine `move`-Regel pro Nutzer: `unique index … on (user_id) where kind = 'move'`.
- Höchstens ein `above` und ein `below` pro Printing: `unique (user_id, kind, card_id, set_code, language, rarity)` (bei `move` sind die Schlüsselspalten null und kollidieren nicht).
- Zielpreis entfernen = `active = false` (Treffer bleiben). Erneut setzen = Upsert mit `active = true, armed = true`.
- Ohne `move`-Zeile ist der Bewegungsalarm aus; Einstellungen zeigen Standardwerte 20 % · 2 € · 7 Tage mit ausgeschaltetem Schalter; Einschalten legt die Zeile an.
- RLS: `for all using (user_id = auth.uid()) with check (user_id = auth.uid())`.

### 4.2 `public.price_alert_events`
| Spalte | Typ / Regel |
|---|---|
| `id` | `bigint generated by default as identity primary key` |
| `user_id` | `uuid not null` |
| `rule_id` | `bigint not null references public.price_alert_rules(id) on delete cascade` |
| `kind` | `text not null` (Kopie aus der Regel) |
| `card_id, set_code, language, rarity` | `text not null` |
| `old_price` | `numeric` (nullable) |
| `new_price` | `numeric not null` |
| `pct` | `numeric` (nullable) |
| `days` | `integer` (nullable; bei `move` das Fenster) |
| `threshold` | `numeric` (nullable; bei Zielpreisen) |
| `day` | `date not null` (UTC-Tag der Auslösung) |
| `created_at` | `timestamptz not null default now()` |
| `dismissed` | `boolean not null default false` |

- `unique (rule_id, card_id, set_code, language, rarity, day)`; Schreiben per Upsert mit `ignoreDuplicates`.
- Index `(user_id, dismissed, id desc)`.
- RLS wie oben; der Auswerter schreibt mit Service-Role.

## 5. Auslöseregel (`alerts.ts`, reiner Helfer)

**Eingaben pro Lauf:** aktive Regeln aller Nutzer; Printings mit `deleted = false`, mindestens einem lebenden Exemplar und `price > 0` (Felder `price`, `price_locked`); Referenzen je benötigtem Fenster über **dieselbe RPC `price_reference(days)`**; letzter Verlaufspreis vor heute je Printing (für `old_price` bei Zielpreisen); Treffer der letzten 30 Tage je Regel (für die Fenster-Sperre). „Heute" = UTC-Datum.

**Ausgabe:** `{ events: [...], armedUpdates: [{ id, armed }] }`.

### 5.1 Bewegungsalarm `move`
- Damals = Referenzzeile nur wenn `day ≤ heute − days`; sonst kein Treffer.
- Quellenfamilie wie G1: Familie(Damals.source) = Familie(`price_locked`), nicht `manual`, nicht unbekannt.
- `deltaUnit = round2(neu − alt)`, `pct = round1((neu − alt) / alt × 100)`; `alt > 0`.
- Auslösen, wenn `|deltaUnit| ≥ min_eur` **und** `|pct| ≥ pct_regel`.
- Sperre: existiert für diese Regel und dieses Printing ein Treffer mit `day > heute − days`, kein neuer Treffer.
- Treffer: `old_price = alt`, `new_price = neu`, `pct`, `days`.

### 5.2 Zielpreise `above` / `below`
- Nur für Printings in der Eingabemenge; fehlt das Printing (gelöscht, keine Exemplare, kein Preis), weder Treffer noch `armed`-Änderung.
- Erfüllt: `above` bei `price ≥ threshold`, `below` bei `price ≤ threshold`; jede Quelle zählt (auch manuell).
- Erfüllt und `armed` → Treffer (`old_price` = letzter Verlaufspreis vor heute oder null, `new_price` = aktueller Preis, `threshold`) und `armed = false`.
- Nicht erfüllt und nicht `armed` → `armed = true` (ohne Treffer).
- Liegt der Preis beim Setzen schon jenseits, löst der nächste Lauf einmal aus.

### 5.3 Reihenfolge und Fehler
- Erst Treffer schreiben (Upsert, `ignoreDuplicates`), dann `armed`-Änderungen. Bricht ein Lauf ab, erzeugt eine Wiederholung am selben Tag keine Dublette; schlimmstenfalls ein doppelter Treffer am Folgetag, nie ein verlorener.
- Die Familienzuordnung liegt in `families.ts` als **markierter dritter Zwilling** von `desktop/electron/price-families.json` / `ml/PriceFamily.kt`; ein Deno-Test vergleicht gegen die JSON-Datei.

### §5.4 Ergänzung nach Abschlussreview

Entschärft (`armed = false`) wird eine Zielpreis-Regel nur, wenn ihr Treffer tatsächlich eingefügt
wurde. Kollidiert der Treffer mit einem Treffer desselben Tages (Upsert mit `ignoreDuplicates`), bleibt
die Regel scharf und löst beim nächsten möglichen Lauf aus, spätestens am Folgetag — wie §5.3 es für
einen abgebrochenen Lauf bereits zulässt. `armed`-Updates werden außerdem nur angewendet, wenn die Regel
seit dem Laden unverändert ist (`updated_at`); ein übersprungenes Update ist kein Fehler, die nächste
Auswertung greift die Regel neu auf. Ergänzend zu §6.1: „Alle erledigt" erledigt nur die zum Zeitpunkt
des Listenladens angezeigten Treffer (`id ≤ größte angezeigte id`), nie Treffer, die danach hinzukamen.

## 6. Desktop

### 6.1 IPC (jeweils `main.cjs` **und** `preload.cjs`)
- `price-alerts-move-get` → Regel oder null; `price-alerts-move-save({ pct, min_eur, days, active })` (anlegen oder aktualisieren).
- `price-alerts-targets-get(printing)` → `{ above, below }` (je `{ threshold, armed }` oder null); `price-alerts-target-save({ printing, kind, threshold })` — `threshold` null/leer setzt `active = false`.
- `price-alerts-events-list` (offen, neueste zuerst, max. 200); `price-alerts-event-dismiss(id)`; `price-alerts-events-dismiss-all`.
- Ohne Cloud-Verbindung: Fehler „Cloud nicht verbunden".

### 6.2 Benachrichtigung
- Neuer Schritt am Ende des Sync-Zyklus: Treffer mit `id > price_alerts_notified_until` (Setting) und `dismissed = false` laden.
- Reiner Helfer `electron/alert-notify.cjs#nextNotification(events, marker)` → `{ notify: 'none'|'one'|'many', event, count, marker }`: Marke leer → Marke auf größte `id`, `none`; ein neuer → `one`; mehrere → `many`; Marke nur vorwärts.
- `one`: Electron-`Notification` mit Text aus `alert-text.cjs` (Kartenname aus lokaler Sammlung, sonst Passcode); `many`: „N neue Preis-Alarme".
- Klick: Fenster nach vorn, Renderer navigiert zu `/insights` Reiter „Alarme".
- Danach Renderer-Ereignis `price-alerts-changed` (preload `onPriceAlertsChanged`).

### 6.3 Ansichten
- **Start:** Karte „Preis-Alarme (N)" direkt über „Bewegungen", nur bei bekannten offenen Treffern; zwei Zeilen mit „Erledigt"; „Alle" → `/insights` Reiter „Alarme".
- **Insights:** vierter Reiter „Alarme" (Wert · Bewegungen · Aufteilung · Alarme): Datum, Text, „Erledigt", oben „Alle erledigt", Zeilenklick → Karten-Panel; leer „Keine offenen Preis-Alarme"; Fehler „Preis-Alarme konnten nicht geladen werden."
- **Karten-Panel:** unter dem Preisverlauf jedes Printings „Preis-Alarm: ≥ [ ] € · ≤ [ ] €"; speichern bei Verlassen/Enter; leer = entfernen; „ausgelöst" neben einem entschärften Zielpreis.
- **Einstellungen › Preise:** Abschnitt „Preis-Alarme": Schalter „Bewegungsalarm", „ab … %", „ab … €", Fenster 7/30 Tage, Hinweis „Ausgewertet wird stündlich in der Cloud. Am Handy erscheinen Treffer beim Öffnen."
- **Deals:** Seitentitel „Deals".

## 7. Handy

- `cloud/PriceAlertsRepository.kt`: Treffer laden (`dismissed=eq.false`, `order=id.desc`, `limit=200`), erledigen, alle erledigen, Bewegungsregel laden/speichern, alle aktiven Zielpreise laden, Zielpreis speichern (Upsert über den eindeutigen Schlüssel) bzw. entfernen.
- `SideStores`: `priceAlertEvents`, `priceAlertMoveRule`, `priceAlertTargets` (je `ListCache`), in `clearAll()` geleert.
- Nachladen: Treffer beim Zurückkehren der App in den Vordergrund (bestehender `repeatOnLifecycle`-Block in `AppNav`) und bei Pull-to-refresh; keine Ladevorgänge bei Seitenwechseln. Regeln/Zielpreise einmal laden, nach eigenem Speichern `refreshAndWait()`.
- **Start:** Karte „Preis-Alarme (N)" über „Bewegungen", nur bei offenen Treffern; zwei Zeilen mit „Erledigt"; „Alle" → Insights Reiter „Alarme".
- **Insights:** dritter Reiter „Alarme" (Bewegungen · Aufteilung · Alarme), Inhalte wie Desktop; Fehler „Preis-Alarme konnten nicht geladen werden — zum Aktualisieren ziehen".
- **Kartendetail:** Zeile „Preis-Alarm: ≥ [ ] € · ≤ [ ] €" unter dem Preisverlauf; speichern mit „Fertig"; leer = entfernen; „ausgelöst".
- **Einstellungen › Preise:** wie Desktop (Schalter, Felder, Chips 7 · 30 Tage, Hinweis).
- **Eingabeprüfung:** reiner Helfer `ml/AlertInput.kt` (Euro mit deutschem Komma > 0; `pct` 1–500; `min_eur` ≥ 0).
- Keine Benachrichtigung am Handy.

## 8. Treffertexte (Zwilling)

`electron/alert-text.cjs` ↔ `ml/AlertText.kt`, gegen `docs/fixtures/portfolio/alert-texts.json`, Kopfkommentare nennen sich gegenseitig.
- `move`: „{Name} · {Set-Code} · {Rarität}: {+/−}{pct} % in {days} Tagen ({alt} → {neu})"
- `above`: „{Name} · {Set-Code} · {Rarität}: Zielpreis ≥ {threshold} erreicht ({neu})"
- `below`: „{Name} · {Set-Code} · {Rarität}: Zielpreis ≤ {threshold} erreicht ({neu})"
- Beträge deutsch mit zwei Nachkommastellen und „ €", Prozent mit einer Nachkommastelle und Komma; gespeichertes `Unknown`/leer bei Set-Code und Rarität → „Unbekannt" (wie G1 §4.12).

## 9. Fehlerfälle
- Cloud nicht erreichbar: Desktop-Fehlermeldung; Handy-Speicher behalten den Stand mit Hinweis; Start-Karte nur bei bekannten offenen Treffern.
- Ungültige Eingaben werden nicht gespeichert, das Feld zeigt den Fehler; die Datenbank-`check`s sichern zusätzlich ab.
- Kein Verlauf: kein Bewegungsalarm, Zielpreise funktionieren.
- Lauf bricht ab: siehe §5.3.

## 11. Einspielen (Nutzer)
1. `supabase/price_alerts_schema.sql` im Dashboard einspielen.
2. Funktion aus dem Repo-Stammverzeichnis deployen: `supabase functions deploy evaluate-price-alerts --no-verify-jwt --project-ref uirfqwklvavgjklgqpnn` (optional vorher Secret `ALERTS_TRIGGER_SECRET` setzen).
3. `supabase/price_alerts_cron.sql` einspielen (stündlich :15).
4. Desktop-Installer **nicht** aus einem Worktree mit `node_modules`-Junction bauen; APK aufs Dev-Handy.
5. Abnahme: Zielpreis knapp unter dem aktuellen Preis setzen, Funktion auslösen oder :15 abwarten → Treffer auf beiden Geräten, genau eine Desktop-Benachrichtigung; „Erledigt" auf einem Gerät entfernt ihn auf beiden.
