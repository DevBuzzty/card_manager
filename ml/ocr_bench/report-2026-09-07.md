## Blocker: connectedDebugAndroidTest kann auf diesem Geraet gerade nicht installieren

`python ml/ocr_bench.py run` scheitert mit:

```
Exception thrown during onBeforeAll invocation of plugin
com.android.tools.utp.plugins.host.apkinstaller.AndroidTestApkInstallerPlugin.
Failed to install APK(s): app-debug-androidTest.apk
INSTALL_FAILED_USER_RESTRICTED: Install canceled by user
```

Das ist genau der in der Aufgabe dokumentierte Fallstrick (der erste androidTest-Install auf
diesem Geraet scheiterte mit INSTALL_FAILED_USER_RESTRICTED), aber die dort genannte Abhilfe
(`adb install -r -t app-debug-androidTest.apk`, dann Gradle) hat diesmal NICHT geholfen. Geprueft,
in dieser Reihenfolge:

1. `adb install -r -t app-debug-androidTest.apk` manuell -- derselbe Fehler.
2. `adb install -r -t app-debug.apk` (die normale App, nicht der Test) -- derselbe Fehler. Das
   grenzt es ein: es ist keine Eigenheit der androidTest-APK, sondern eine generelle
   Installationssperre auf diesem Geraet gerade jetzt.
3. `pm list packages` zeigt `com.example.yugiohscanner` ueberhaupt nicht installiert -- die App
   fehlt komplett auf diesem Geraet im Moment (kein Signatur-/Upgrade-Konflikt).
4. `dumpsys window` zeigt `isKeyguardShowing=true` bei gesperrtem Bildschirm; `locksettings
   get-disabled` liefert `false` (die Sperre ist aktiv, kein PIN-loses Geraet). Bildschirm per
   `adb shell input keyevent KEYCODE_WAKEUP` geweckt -- Sperre blieb bestehen (`wm
   dismiss-keyguard` aendert nichts, ein Wisch-Swipe auch nicht -- erwartbar bei aktivem PIN).
5. APK direkt auf das Geraet gepusht und per `adb shell pm install` (ohne den Gradle/UTP-Umweg)
   installiert -- derselbe INSTALL_FAILED_USER_RESTRICTED. Das schliesst adb/Gradle als
   Fehlerquelle aus; es ist eine Geraete-/Systementscheidung.
6. Waehrend der Untersuchung wurde das Geraet zwischenzeitlich entsperrt (`dumpsys window` ging
   von `isKeyguardShowing=true` auf `isKeyguardShowing=false`). Install erneut versucht (Schritt 1
   wiederholt) -- **derselbe Fehler, trotz entsperrtem, eingeschaltetem Bildschirm.** Das
   widerlegt die reine "Bildschirmsperre"-Erklaerung: eine gesperrte Bildschirmsperre WAR
   wahrscheinlich Teil des urspruenglichen Zustands, ist aber nicht die ganze Ursache.

Das passt zu einem bekannten MIUI/Xiaomi-Verhalten: neben "USB-Debugging" gibt es unter
Einstellungen > Weitere Einstellungen > Entwickleroptionen einen SEPARATEN Schalter (oft
"Installation via USB" oder "USB-Debugging (Sicherheitseinstellungen)"), der zusaetzlich
aktiviert sein muss, damit `pm install`/`adb install` ueberhaupt greift -- unabhaengig vom
Sperrbildschirm. Das Umlegen dieses Schalters verlangt typischerweise eine Mi-Konto-Anmeldung samt
Netzwerk-Verifikation und laesst sich nicht aus der Ferne per ADB setzen (und sollte es auch
nicht -- das eigenmaechtige Aendern von Sicherheitseinstellungen auf dem Geraet des Nutzers liegt
ausserhalb dessen, was ein Agent tun darf). **Es braucht eine Person am Geraet**, die diesen
Schalter einmalig prueft/aktiviert, danach reicht:

```
python ml/ocr_bench.py run     # Geraet muss entsperrt/an sein, "Installation via USB" aktiviert
python ml/ocr_bench.py pull
python ml/ocr_bench.py score
```

(`build` und `push` muessen nicht wiederholt werden -- der Korpus liegt schon auf dem Geraet und
lokal unter `ml/data/ocr_bench_work/`, git-ignoriert.)

## Was diese Messung ohnehin nicht abdeckt (unabhaengig vom Blocker)

- Katalog-Gate auf der Passcode-Korrektur: `OcrBench.kt` ruft `OcrText.findPasscode` ohne
  Katalog-Anbindung auf (immer-true-Gate) -- der Messkorb braucht keine importierte catalog.db
  auf dem Geraet. Das misst OCR-/Zonen-Qualitaet, nicht Katalog-Politik.
- Detektorqualitaet: die Box kommt aus dem Manifest (Rig: aus dem Dateinamen; eBay: aus
  `measure_zones.detect_box()`), nicht aus dem On-Device-Detektor. Absichtlich -- das isoliert
  OCR/Zonen von der Detektion, die ein eigenes, bereits ausgeliefertes Thema ist.
